# Task: img-04, image update state over MQTT and as Home Assistant `update` entities

This is phase 4 of the image update check (design §7.4 and §8 step 3, MQTT/HA part only).
It publishes each entry's image update state as a retained MQTT topic. It adds a
read-only Home Assistant `update` entity per published entry and a hub "Updates
available" sensor. Everything goes through the existing reconcile. It ships in 0.12.0.

Registry credentials (`img-05`) are **out of scope**: the operator has no private
registries.

## Notes from `img-02` and `img-03`, verified by the orchestrating session

- **Shown state:** use `image_update.effective_state(entry)` or
  `image_update_ui.image_update_info(entry)`, never the raw `image_update_state`. The
  stored column is stale while the check is off. The info dict has `latest`, `kind`,
  `model`, `tag`, `running_version`, `release_url`, `pushed_at` and `checked_at`.
- **Digest-model `latest`** is stored as `sha256:<12 hex>`. Build `<tag>@<first 7 hex>`
  for `installed_version` / `latest_version`, with the OCI `version` label (from
  `image_info`) in `release_summary` when known.
- **Change detection:** `image_update.apply_evaluation` returns True when
  `(state, latest)` changed, and `RegistryProvider._recompute_all` loops over entries.
  That is the natural hook to request a non-forced sync. Nothing is published when
  nothing changed.
- **Missing from the sync trigger:** the new columns are **not** in
  `notify_state._ENTRY_ATTRS` today, so image state changes don't trigger a sync. Decide
  whether to add the computed columns there or to trigger explicitly from the job. Avoid
  double syncs, and record the choice.
- **Switch off:** withdraw the HA `update` entities and stop publishing per-entry image
  topics (clear the retained ones) through the normal reconcile. The hub sensor should
  report 0, or be withdrawn; pick one and record it.
- **Switching on or off** fires a full sync. `on_settings_changed` is the hook, and both
  the UI and the API call it.

## What to do

1. **State topic** `<base>/entry/<id>/image` (retained), for entries whose effective state
   is not `off`. The payload follows §7.4: `installed_version`, `latest_version`,
   `title`, `release_url`, `release_summary`, `state`, `kind`, `checked_at` and
   `std_entry_id`.
   - **Tag model:** `installed_version` is the running tag, and `latest_version` is the
     newer tag (or the running tag when current).
   - **`unknown`, `error` and `pinned`:** `installed_version` is null, so HA shows the
     entity as unknown. For `pinned`, check whether a sensible non-null pair reads
     better, and record your choice.
   - Respect per-entry `ha_publish` and the existing publish rules exactly as the other
     entry topics do.
2. **Additive fields:**
   - `<base>/summary` gains `updates`: the count of effective `update` states.
   - `<base>/entry/<id>/state` gains `image_update_state`.
   - Don't change any existing key.
3. **HA discovery** (in `notify_ha.py`, reconciled only by `notify_state.full_sync()`):
   - one `update` entity per published entry that has an image and a policy other than
     `off`:
     - object id `entry_<id>_image`, unique id `<node>_entry_<id>_image`;
     - `state_topic` is the image topic, with **no `command_topic`** (read-only);
     - `entity_category: diagnostic`, `availability_topic` `<base>/status`, and no
       `entity_picture`;
   - a hub `sensor` "Updates available" (`hub_updates`, `value_json.updates`).
   - Purge, opt-out, soft delete and channel removal must clear them through the existing
     mechanisms (`notify_purge.py`). Don't add a second mechanism.
   - Check the HA MQTT `update` docs for the exact config keys. The design verified them
     on 2026-11-21.
4. **Never block producers:** publishing goes through `enqueue`, and purge runs on the
   publisher thread through `Publisher.call()`, as today. The image update job must never
   wait on the broker.
5. **Tests:**
   - topic and payload for each state and both models;
   - the digest version formatting;
   - summary `updates`;
   - the additive `state` field;
   - the HA config of the `update` entity and the hub sensor;
   - withdrawal when the check is switched off;
   - withdrawal on per-entry policy `off` and on opt-out, purge and soft delete;
   - no publish when nothing changed;
   - a full sync on toggle;
   - updates never affecting health or the State sensors.
   - Use the existing fake publisher and broker patterns, with no real network.
   - Run `uvx ruff@0.15.17 check .` and the FULL suite
     (`uvx --with-requirements requirements-dev.txt pytest -q`); both must pass.
