# Task: Certificate-expiry condition on HTTPS checks

Add an optional **minimum days left** to HTTPS checks, covering both URL checks
(internal/external) and HTTP service checks. Once the condition is set, a check
fails with `cert expires in N days (min 7)` when the leaf certificate is too
close to expiry, even if the HTTP status is fine. This is the second chunk of
v0.9.0. Chunk 01 (`prompts/done/2026-11-16-v090-01-dns-check.md`) already
added the `dns` check type; read it and its commit to see how a check field
goes through every layer, then do the same here.

## What to do

1. **Dependency.** Parsing the certificate needs `cryptography`, because the
   stdlib can't decode a DER cert from an unverified handshake.
   - Add it to `requirements.in`.
   - Regenerate with `--upgrade-package cryptography` only, so no unrelated
     bumps.
   - Confirm the Docker build still works on `python:3.11-slim`, which has
     manylinux wheels: run `docker build .` if Docker is available, otherwise
     note it.
   - Record the choice in `docs/decisions.md`. The rejected alternatives are
     a hand-rolled ASN.1 walker and the private `ssl._ssl._test_decode_cert`.

2. **Model and migration.** Add these nullable columns to `health_check`:
   - `cert_min_days` (Integer): the condition. NULL means off.
   - `last_cert_expires_at` (DateTime, naive UTC): cached, set by the
     checker.

   Write one Alembic migration on top of chunk 01's head, and add
   `cert_min_days` to `to_config()` and to restore.

3. **Probe.**
   - `probe_http(..., cert_min_days=None)`. When `cert_min_days` is set and the
     target scheme is `https`, also read the leaf cert. Do a separate TLS
     handshake to the **target URL's** host and port (default 443) with SNI set
     to the hostname. Use `ssl.create_default_context()`, set
     `check_hostname=False` and `verify_mode=CERT_NONE` so it works when
     verify-TLS is off, and call `getpeercert(binary_form=True)`. Parse
     `not_valid_after_utc` with `cryptography.x509`, and use the probe's
     `timeout`.
   - Return the expiry in a new `ProbeResult.cert_expires_at` (aware or naive
     UTC; be consistent with what `jobs.py` stores).
   - Result rules, in this order:
     1. The HTTP result fails: keep today's HTTP failure message, but still
        report the expiry if the handshake got one.
     2. HTTP is ok and the remaining time is less than `cert_min_days` days:
        `ok=False`, message `cert expires in N days (min M)`, where N is the
        whole days left, floored. If the cert has already expired, the message is
        `cert expired N days ago`.
     3. HTTP is ok but the cert couldn't be read (handshake error or
        timeout): `ok=False`, message `cert check failed: <reason>`.
     4. Otherwise ok, and the status code is kept.
   - `http://` targets ignore `cert_min_days`: no handshake, and
     `cert_expires_at` is None.
   - `jobs.py` passes `cert_min_days` in the job, and writes
     `last_cert_expires_at` from the result. Clear it when the check has no
     condition or is plain http, so a stale date never shows.
   - URL checks use the entry's current internal or external URL. If that URL
     is http, the condition is ignored.
   - Note in decisions.md that the separate handshake bypasses any
     `HTTPS_PROXY` that `requests` would honour.

4. **Validation and form.**
   - `cert_min_days` is optional; when set it must be an integer from 1 to
     365.
   - It is allowed on URL checks and on http service checks. On
     tcp/ping/dns service checks it is rejected in the API with a 400, and the
     form never submits it.
   - Saving an http:// URL with a value is allowed: the value is stored and
     ignored at runtime, because the URL can change underneath (notifier,
     synthesizer).
   - Form names: `uc_<which>_cert_min_days` and `svc_<key>_cert_min_days`. Add
     it to `_signature` so a change resets the cached state.

5. **UI.**
   - Add a "Min cert days" number input next to Verify TLS on URL-check rows
     and on HTTP service rows.
   - **Hide it unless the effective URL starts with `https://`**: for URL
     checks, the entry's internal or external URL input on the same form; for
     service checks, the target input. Update it live on input.
   - Placeholder "off". A failed submit re-renders the value.

6. **Detail panel.**
   - `check_payload` includes `cert_min_days` and `cert_expires_at` (ISO-Z,
     using the module's helper).
   - When an expiry is known, the panel shows "Cert expires
     2027-02-01 (77 days)", in the local display format the panel already
     uses for dates.
   - Highlight it in the failing colour when it is below the minimum.

7. **Management API and MCP.**
   - The check create and patch schemas accept `cert_min_days`, nullable
     (null clears it). Patch accepts it on URL checks and on http service
     checks; anything else is a 400.
   - `CheckOut` returns `cert_min_days` and `cert_expires_at`, and OpenAPI
     picks them up.
   - MCP: `add_check` gets `cert_min_days`, and `CHECK_PATCH_FIELDS` gets the
     key. The docstrings give the Emmett example: a URL check on
     `https://em-pve01.crzynet.me:8006/` with `{"cert_min_days": 7}`, and
     Proxmox's self-signed cert with `verify_tls` false still reports its
     expiry.

8. **Tests** (no real network):
   - Mock the handshake helper. Factor it as `_read_cert_expiry(host, port,
     timeout)` so it is easy to patch, and generate a throwaway self-signed

   - Cover:
     - pass above the minimum;
     - fail below it with the exact message;
     - the already-expired message;
     - HTTP failure keeps the HTTP message and still reports the expiry;
     - a handshake failure gives `cert check failed: ...`;
     - http:// skips the handshake (assert it is not called);
     - it works with `verify=False`;
     - the job write-back sets and clears `last_cert_expires_at`.

   - API: allowed on URL checks and on http service checks, a 400 on tcp

   - The migration, and passing the MCP argument.
   - Detail payload fields.
