# Task: Rotate an API key (Settings → API)

Add a **Rotate** action to each active key in Settings → API. Rotating keeps
the key's row (id, name, scope, created_at and audit history) but issues a new
secret. The new full key is shown **once**, on the same "key created" page as
for creation. The old secret stops working immediately. A new **Rotated**
column shows when the key was last rotated. This is the third chunk of v0.9.0
and runs after `v090-01` (DNS check) and `v090-02` (cert expiry). Its
migration goes on top of their heads.

## What to do

1. **Model and migration.** Add a nullable `rotated_at` DateTime (naive UTC)
   column to `api_key`. Write one Alembic migration whose `down_revision` is
   the current single head (check with `alembic heads`). Add no other columns.

2. **`api_keys.rotate_key(key)`.**
   - Refuse a revoked key: raise `ValueError` or return None, and match the
     module's style.
   - Generate a fresh key with the same `generate_key()`, so both the prefix
     and the secret are new. Replace `prefix` and `key_hash`, set
     `rotated_at = utcnow()`, and clear `last_used_at` and `last_used_ip`
     (they described the old secret).
   - Return the full new key.
   - There is no grace period: the old secret is rejected at once, because
     `verify` looks the key up by prefix and the hash.

3. **Route** `POST /settings/api-keys/<int:id>/rotate`.
   - Admin only and CSRF-protected, exactly like revoke.
   - On success, render `api_key_created.html` with the new key and the same
     no-store/no-cache headers as the create route. Make the template say
     "Key rotated" rather than "Key created" when it's a rotation: pass a
     flag, and don't copy the template.
   - A revoked or unknown key: flash an error and redirect back to the API
     tab.
   - Log a line with the key **id** only. Never log the name, prefix or
     secret; the CodeQL clear-text-logging rule flagged key-derived values
     before.

4. **UI (Settings → API key list).**
   - Add a **Rotated** column showing the date (or "—"), in the same date
     format the list already uses.
   - Add a **Rotate** button next to Revoke on active keys only, with a JS
     `confirm()`: "Rotate '<name>'? The current key stops working
     immediately; you'll get a new one to copy."
   - Revoked keys show neither button.
   - Match the existing button styling.

4b. **Let a revoked key's name be reused.** Today `api_key.name` is
   `unique=True` across every row, and `validate_name` says "revoked keys keep
   their name", so once a key is revoked its name can never be used again.
   - Make names unique among **active** keys only. In the same migration as
     `rotated_at`, drop the column-level unique constraint and add a partial
     unique index `ux_api_key_name_active` on `name WHERE revoked_at IS NULL`.
     SQLite supports these.
   - SQLite can't drop a constraint in place, so use `batch_alter_table`, and
     check how the earlier migration `d4a9e2c6b715` named the constraint or
     index.
   - Mirror the change in the model's `__table_args__` (`sqlite_where`), and
     remove `unique=True` from the column.
   - Change `validate_name` to check active keys only, and update its message.
   - The audit log already keeps a `key_name` snapshot plus `api_key_id`, so
     old audit rows still point at the old (revoked) row. Confirm the audit
     key filter in Settings → API still tells the two apart: if it filters by
     name, switch it to id or label revoked keys "(revoked)".
   - Tests:
     - creating a key with a revoked key's name works;
     - a name clash with an active key is still rejected, both in the form and
       at the DB level (IntegrityError);
     - the migration upgrade and downgrade both work. The downgrade may fail
       if duplicates exist; make it fail with a clear message, or document
       it.
   - CHANGELOG → Fixed: "A revoked API key's name can be used again for a
     new key."

5. **Not in the management API.** Key management stays UI-only: §14.8 keeps
   users and keys out of the API. Note this in decisions.md.

6. **Tests:**
   - `rotate_key`: the new prefix and hash differ from the old ones; the old
     full key fails `verify` and the new one passes; scope, name and id are
     unchanged; `rotated_at` is set; `last_used_*` is cleared.
   - A revoked key can't be rotated.
   - The route: the admin gets the page with the full key once and no-store
     headers; a non-admin is refused; the CSRF check is enforced the same
     way as revoke's tests; a revoked key redirects with a flash.
   - A management API call with the old key returns 401 after rotation, and
     with the new key returns 200 on `/api/v1/whoami`.
   - The Settings list shows the Rotated column and value.
   - The migration test, matching the existing ones.

7. **Docs** (same commit):
