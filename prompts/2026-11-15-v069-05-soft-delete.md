# Task: Soft-delete for service entries (PRD §12.5)

Deleting a service is currently a permanent hard delete. Make it a recoverable soft delete with a retention window, a Settings → Deleted tab, a purge job, and resurrect-on-register.

## What to do

1. Migration: `service_entry.deleted_at` DateTime, nullable, plus an index.
2. Model helper: `ServiceEntry.active()` (a query filtered on `deleted_at IS NULL`). Audit **every** `ServiceEntry.query` call site (`grep -rn "ServiceEntry.query" --include='*.py' .`; there are about 18). List each one in your report with its decision: active-only, or deliberately all rows. Dashboards, health-check loop, widget refresh, badges, and the group "has services" check are active-only. The register lookup must see deleted rows (step 4).
3. Both delete paths (edit-page form and `/api/v1/entries/<id>/delete`) set `deleted_at = now` and commit. Leave the widget attached and delete nothing else. Update the flash and confirm-popover copy to say the entry can be restored from Settings → Deleted for N days.
4. **Resurrect on register:** in `upsert_service`, a matching `(host, container_name)` row with `deleted_at` set gets `deleted_at = None` and is then updated as normal, with an INFO log line. Make sure the match prefers an active row if both an active and a deleted row exist.
5. Settings → **Deleted** tab: lists soft-deleted entries (name, host, deleted-at, days until purge) with **Restore** and **Delete permanently** buttons (POST, admin-only, CSRF token if v069-04 has landed). Delete permanently calls a single `hard_delete_entry(entry)` function. Move the existing hard-delete code (widget-if-unused deletion) into it **unchanged**, so v069-06 changes only that one function.
6. Setting `deleted_retention_days` (int, default 30; `0` purges at the next run). Add a daily APScheduler job at 00:25 that calls `hard_delete_entry` for rows past the window.
7. Backup/restore: include `deleted_at` in YAML backups, and restore it (NULL when absent, so v0.6.8 backups still restore). `/dbdump`: show deleted rows marked, or add a filter. Your call; record it.
8. Tests: delete hides the entry from the dashboard query and the health loop's query; restore brings it back; the purge removes rows past the window and keeps rows inside it; a register resurrects the row with its curated `group_id`/`sort_priority` intact; a backup round-trips `deleted_at`.
